# MamboChat 上下文缓存使用建议

> 面向普通用户。本文档帮助你理解:哪些日常操作会让长对话的输入费用变高,哪些不会,以及如何养成省钱的使用习惯。
> 只涉及费用,不影响回答质量。

---

## 一、什么是上下文缓存

每次向 AI 发送消息时,为了让模型"记得"之前的对话,系统会把**从第一条消息开始的整个对话内容**重新发送一遍。对话越长,每次发送的内容越多。

服务商(如 DeepSeek)提供了一项自动优化:如果两次请求的**开头部分完全一样**,那么这段重复的开头会被缓存,命中缓存的部分按**更低的价格**(约为原价的 1/10)计费。

关键规则:

- **必须一字不差**:缓存要求从第一条消息开始的前缀完全一致;前缀一旦变动,变动点之后的内容在**该次请求**中按原价计费。
- **越靠前越关键**:请求的开头(系统提示词区域)任何变动,会导致整个会话缓存全部失效;只改对话末尾的消息几乎没影响。
- **缓存会过期**:如果隔了较长时间没有继续对话,缓存会自然失效,下一次请求按原价计费,这属于正常现象,无需处理。
- **只影响费用**:是否命中缓存与回答质量完全无关。

> **适用范围**:本文分析的是**同一个会话进行中**变更配置或内容后,继续该会话时对缓存与支出的影响。如果你先调整好配置,再**新建会话**开始对话,就不必担心这些影响——新会话会重新建立自己的缓存;旧会话只要不再继续,其缓存也不会因配置改动而受损。

## 二、哪些操作会破坏缓存

判断一次操作会不会破坏缓存、代价多大,只需看一点:**这次改动最终落在请求的哪个位置**。

请求的结构是固定的:

```
系统提示词(最开头) + 历史消息(按时间顺序)
```

- 改动落在**系统提示词** → 整个会话缓存全部失效(严重)
- 改动落在**历史消息**中间 → 从该处开始失效(程度取决于位置)
- 改动**不进入请求内容** → 不影响缓存

> 注意:缓存被破坏后,**只有紧接着的第一次请求**会按原价计费;之后系统会以新的前缀重建缓存,后续请求重新享受缓存价格。

### 1. 改动"系统提示词"内容 → 严重:整个会话缓存全部失效

**这是影响最大的一类。** 系统提示词位于每次请求的最开头,任何变动都会让整个会话的缓存从头失效,**之后第一次请求将按原价计费**(随后缓存会以新前缀重建,后续请求恢复正常优惠)。

关键在于:**无论通过哪个功能入口修改,效果完全一样**。比如"修改 Agent 的系统提示词"和"修改会话的系统提示词",对缓存的影响完全相同——都是全量失效。

常见入口(前端功能):

| 前端操作 | 说明 |
|---------|------|
| 修改**会话设置**里的系统提示词 | 直接改写提示词 |
| 修改 **Agent 编辑**里的系统提示词 | 与上面影响完全相同 |
| 挂载、修改、发布新版本**系统提示词资源** | 资源内容会拼进提示词 |
| 在**会话设置**中挂载或切换**消息模板** | 模板内容会拼进提示词(与输入框工具栏挂载不同,见第 2 类) |
| 修改**知识库的名称或描述** | 知识库信息写在提示词里(改文档内容则不影响,见第 3 类) |
| 修改**技能的名称或简介** | 技能列表写在提示词里(改技能内部文件则不影响,见第 3 类) |
| 修改**子代理的名称或简介** | 子代理列表写在提示词里 |
| 切换**联网搜索模式**(关闭 / 直接读取 / 搜索并读取) | 模式说明写入提示词,同时改变可用工具 |
| 挂载/卸载 **MCP 服务**,启用/停用**建议工具** | 工具信息写入提示词 |
| 修改挂载**后端的描述** | 后端说明写入提示词 |
| 切换**模型或服务商** | 不同模型的缓存完全不通用,必然全量失效 |

### 2. 改动"历史消息"内容 → 影响取决于位置

- **修改或删除历史消息** → 从被修改的消息开始,其后的缓存全部失效
- **从中间某条消息重新生成** → 从该消息开始失效
- **切换消息分支** → 从分支点开始失效
- **在输入框挂载消息模板后发送**(工具栏挂载)→ 模板内容会注入这条消息,并按模板的"参与长度"设置参与后续几轮上下文;参与轮数用尽后,模板会从后续请求中消失,前缀在**挂载模板的那个问答对**处发生变化,该位置之后的缓存随之失效

> 规律:改动越靠前、会话越长,代价越大;只改动最后一条消息时,影响很小。
> 关于工具栏挂载模板:破坏范围限于挂载模板的那个问答对及其之后,**不是整个会话**;若把模板的"参与长度"设为 0,模板不进入上下文,则不影响缓存。

### 3. 修改"不进入请求"的内容 → 不影响缓存

- **知识库内部的文档内容**(重新上传、更新切片)——检索发生在回答过程中,不占用开头位置
- **技能内部文件内容**——技能按需读取,文件内容不进入提示词

### 4. 主动压缩历史 → 划算

- **压缩历史(手动摘要)**:压缩点之前的对话被替换成一段简短摘要。这会"破坏"原有缓存,但这是**故意的、划算的**操作——之后的每次请求都大幅变短,长期看显著省钱。
- **自动摘要**:与手动压缩同理,是系统在会话过长时自动执行的省钱机制。

## 三、哪些操作不破坏缓存(放心用)

以下日常操作不会影响缓存命中:

- 正常发送新消息、上传附件、追问
- 修改**知识库里的文档内容**(重新上传、更新切片)
- 修改**技能内部文件内容**
- 从某条消息**重新生成**回复(新请求只包含到该消息为止的历史,正好复用已有缓存,反而省钱)
- 查看历史版本、对比差异、**回滚工作区文件**(版本控制/回滚针对的是工作区文件内容,不进入请求前缀;回滚记录也不会进入上下文)
- 修改会话**标题**、归档、导出、导入会话
- 查看请求报文、切换界面主题等纯展示操作

> 注意区分:这里说的是**工作区文件的版本控制/回滚**。若在"资源管理"里回滚**系统提示词、消息模板**这类会拼进提示词的资源版本,仍属于第 1 类,会破坏缓存。

## 四、省钱实操建议

1. **配好再聊**:开始长对话前,一次性配置好系统提示词、挂载资源、消息模板、联网搜索模式,中途尽量不再调整。
2. **长会话慎动开头**:任何会改写系统提示词的操作(改会话或 Agent 的提示词、换挂载、改技能/子代理简介等),在长会话中代价都相同且最大——必须调整时,优先考虑**新建一个会话**。
3. **纠正回答的两种方式都省钱**:对 AI 的回答不满意时,有两种常见做法——对目标消息点击**重新生成**,或直接发一条新消息指出问题。两者都不破坏缓存:重新生成只携带到该消息为止的历史,正好复用已有缓存;直接纠正只是往末尾追加新消息,前缀完整命中。区别在于:重新生成会替换掉旧回答,后续历史更干净;直接纠正则保留旧回答,后续每次请求都要携带它。真正伤缓存的是**编辑早期消息后再重发**,那会从被改的位置起失效。
4. **适时压缩历史**:会话变得很长时,主动使用"压缩历史"功能,比一直以全价发送完整历史更省钱。
5. **模板挂载要节制**:在输入框挂载消息模板时,留意模板的"参与长度"设置;频繁挂载、切换模板,会在模板过期消失时反复造成前缀变化。
6. **工具开关保持稳定**:联网搜索、MCP、子代理、技能等开关,在会话进行中尽量保持不变。
7. **缓存过期不必担心**:隔了很久再继续对话,第一次请求按原价计费是正常现象,继续对话后缓存会重新建立。
