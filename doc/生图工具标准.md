# 生图工具标准 v2.1

MamboChat 的生图能力通过一份**工具契约**接入。后端有两种来源：

1. **MCP 服务**——任何 MCP 服务，只要提供下列三个固定工具并遵守返回约定，
   即可在「设置 → 生图工具」里被选为生图后端；
2. **系统模型**——系统里已配置的、能输出图片的 Chat 模型（平台内置实现，
   章节「内置模型后端」）。

> 注意：这里的 MCP **只是通信与接入协议**。平台在中间件层把这三个工具包装成普通
> LangChain 工具交给 Mambo Agent，MCP 服务本身不会作为 MCP 工具暴露给 LLM。

---

## 一、标准契约

| 工具名 | 参数 | 必须返回 |
|---|---|---|
| `image_generate` | `prompt: str`（必填）<br>`resolution: str = "1024x1024"`<br>`negative_prompt: str \| null`<br>`count: int = 1`<br>`sync: bool = true`<br>`extra: object = {}`<br>`reference_images: ImageContent[] \| null` | `{"task_id": "<非空字符串>"}`（可附加 `status` / `count` / `resolution` / `reference_count`） |
| `image_task_status` | `task_id: str`<br>`wait_timeout: int = 0` | `{"task_id", "status", "progress", "count", "error"}` |
| `image_download` | `task_id: str`<br>`index: int \| null`<br>`wait_timeout: int = 0` | 1..N 个 **`ImageContent`**（必须带 base64 数据 + `mimeType`） |

> LLM 看到的 `image_download` 还带 `path`（必填，落盘目录）与 `prefix`（文件名前缀）——
> 这两个是**平台侧参数**，不会透传给 MCP 服务，服务只需要处理 `task_id` / `index` / `wait_timeout`。

- `status` 取值：`queued` / `running` / `completed` / `failed` / `expired`
  （`pending` / `success` / `done` / `error` 等别名会被平台归一化）。
- `progress` 允许为 `null`（同步型后端没有真实进度）。平台会把 `"50%"`、`0.5` 之类归一为 0~100。
- 返回可以是 MCP 的 `structuredContent`，也可以是文本里的 JSON。
  FastMCP 默认的 `{"result": {...}}` 包裹会被平台自动展开。

### `resolution` —— 分辨率

- 格式为 `宽x高`（也接受大写 `X`、`*`、`×`、`：` 等分隔符），单位像素，
  两侧取值 64 ~ 4096，例如 `1024x1024`、`768x1344`。
- 平台会把它解析成 `width` / `height` 两个键合并进 `extra` 一起下发；
  服务也可以直接读取 `resolution` 原始字符串（服务自己的实现优先）。
- `extra` 中**显式**给出的 `width` / `height` 优先级高于 `resolution` 解析结果。
- 服务若不支持自定义分辨率，必须**忽略**该参数并使用自身默认值，不能报错。
- 配置项「默认分辨率」对应平台侧默认参数，LLM 不传时按该值下发。

### `wait_timeout` —— 状态工具阻塞等待

- 单位秒，缺省 `0` 表示**不等待**，立即返回当前状态（兼容旧行为）。
- `wait_timeout=30` 表示最多阻塞 30 秒返回状态：服务内部按短周期轮询任务，
  一旦任务进入 `completed` / `failed` / `expired`（或进度达到 100%）**立即提前返回**，
  不必等满 30 秒。
- 超时后仍返回当时的最新状态（可能是 `running`），不算错误。
- 平台侧 `image_download` 也接受同名参数：带该值时先等待任务收敛再取图。
- 平台会把 `wait_timeout` 归一化为 0~300 之间的整数。

### `reference_images` —— 参考图

用于图生图 / 风格或人物参考。**能力必须显式声明**：

- 支持的实现：在 `image_generate` 的 inputSchema 里声明 `reference_images` 字段；
- 不支持的实现：**不要声明**该字段——平台检测不到就整条屏蔽，LLM 根本看不到这个参数
  （而不是“传了再报错”）。

字段类型就是 MCP 协议自己的 `ImageContent`（FastMCP 可直接注
`Optional[List[ImageContent]]`），arguments 里收到的样子：

```json
{
  "prompt": "把这只狐狸画成水彩风",
  "reference_images": [
    {"type": "image", "data": "<base64>", "mimeType": "image/png"}
  ]
}
```

传递链条：

1. **LLM 只给 workspace 虚拟路径**，例如 `["/.mambo/chat_user_file/<file_id>.png",
   "/workspace/images/fox_20261029_170221_0.png"]`（用户上传的图由平台落到
   `/.mambo/chat_user_file/`，平台生成过的图在 `/workspace/images/`）；
2. 平台读取文件、按文件头校正 mime、编码为 base64，再以 `ImageContent` 数组下发；
3. 实现类**必须真正消费**这些参考图——静默忽略会产出用户不想要的结果，属于违规。

硬性限制（超限直接报错，不做静默裁剪）：

| 限制 | 取值 |
|---|---|
| 张数 | ≤ 8 |
| 单张体积 | ≤ 8MB |
| 合计体积 | ≤ 20MB |
| 格式 | `image/png` / `image/jpeg` / `image/webp` / `image/gif` / `image/bmp` |

实现侧还要自行校验：base64 无法解码、mime 非 `image/*`、数据为空、超限，
都应返回错误（`isError=true` + 文本），不允许吞掉。

## 二、服务的硬性义务

1. `extra` 里的键**原样透传**给底层引擎；不认识的键必须忽略，不能报错。
2. 与标准参数同名的 `extra` 键会被平台过滤，不会覆盖契约字段。
3. `sync=true` 时阻塞上限建议 ≤ 90 秒，超时必须回落为异步并返回 `task_id`。
4. **任务状态由服务自己持久化**。stdio 传输下平台每次调用都会启动新进程，
   状态不能放在进程内存里（参考实现用临时目录 JSON 文件示范）。
5. 失败时返回 `isError=true` + 文本说明，不要抛协议级异常。
6. `image_download` **只返回图片数据**，不返回 `ResourceLink` / URL —— 
   平台不会再去下载，返回链接会被判定为不合规。
7. 服务不需要关心落盘位置：`path` / `prefix` 由平台处理。
8. `resolution` 不支持时必须忽略而非报错；`wait_timeout` 若服务不实现阻塞，
   平台会自行轮询兜底（见 `run_status`），行为依然符合标准。
9. `wait_timeout` 的耗时计入本次工具调用，因此服务侧实现必须尊重
   「状态收敛即提前返回」，不能无条件等满超时。
10. **声明了 `reference_images` 就必须严格处理**：数量超限、base64 无法解码、
    mime 非图片、体积超限、数据为空，一律返回错误而不是忽略。参考图要真正参与
    生成（可以是风格 / 内容 / 构图任一种影响），不得丢弃。

## 三、平台侧行为

1. **劫持**：平台直连 MCP 会话取原始 `CallToolResult`，解析 `ImageContent`
   （绕过通用 MCP 工具通道，因此不受其"只保留文本"的格式化影响）。
2. **落盘**：图片写入 Agent 工作区，返回虚拟路径。`path` 是**必填**参数，
   必须位于 `/workspace` 之下；缺失、相对路径、盘符、UNC、`..` 越界
   **一律报错**，框架不做任何回退。`prefix` 缺省为 `image`，非法时报错。
3. **命名**：`{prefix}_{YYYYmmdd_HHMMSS}[_{index}].{ext}`，扩展名按 mime 推导，
   `prefix` 仅允许 `[A-Za-z0-9_-]{1,64}`。
4. **不回传图片数据**：下载工具只把路径交给 LLM，图片不进上下文（省 token）。
   需要展示给用户时，由 LLM 调用 `show` 工具（`show` 会自己读工作区并落 file_id）。
5. **前端可见**：启用的工具名（标准三件套 / 一条龙）都会注册到内置工具追踪器，
   调用过程以工具子消息展示；`image_generate_show` 与 `show` 一样额外产出一条
   FILE 子消息，图片直接渲染在对话里（多图按 `files` 顺序各出一条）。
6. **默认参数**：配置里的「默认数量 / 默认分辨率」在 LLM 未显式传 `count` / `resolution`
   时生效；`resolution` 解析出的 `width` / `height` 会被 `extra` 中的显式同名键覆盖。
7. **等待兜底**：`wait_timeout` 先由服务侧实现（一次调用内完成等待）；
   若服务未实现阻塞（状态仍为 `queued`/`running`），平台在本次调用内自行短轮询兜底，
   最长不超过配置的 `wait_timeout`，且状态收敛即提前返回。
8. **参考图能力**：配置项 `supportsReferenceImages` 三态——`null` 表示自动
   （MCP 后端连一次服务，看 `image_generate` 的 inputSchema 是否声明
   `reference_images`，结果在进程内缓存；模型后端按「支持」处理），
   `true` / `false` 表示手动钉住；「检测」按钮会显示 MCP 侧的探测结果并可回填配置。
   配置页对两种后端都允许手动选择。不支持时该参数不会出现在工具 schema 与描述里。
9. **参考图校验**：LLM 给的是路径，平台负责读文件、嗅探真实 mime、校验张数 /
   单张与合计体积 / 格式，并校验路径必须是 `/workspace` 之下的绝对虚拟路径
   （裸 `..`、`//`、盘符、UNC、根目录一律报错）。任何一步不通过都直接报错，
   不静默裁剪、不静默丢弃。
10. **`extra` 与参考图互斥**：`extra` 里同名键（`reference_images` / `mode` /
    `path` / `prefix` / `wait_timeout` / `resolution` …）会被过滤，不能覆盖契约字段。

## 四、返回值示例

```json
// image_generate
{"task_id": "task_1793264511_171bbcb5", "status": "completed", "count": 2, "resolution": "1024x1024", "reference_count": 1}

// image_task_status（wait_timeout=30，任务第 4 秒完成 → 提前返回）
{"task_id": "task_1793264511_171bbcb5", "status": "completed", "progress": 100, "count": 2, "error": null}

// image_task_status（wait_timeout=30，30 秒仍未完成 → 返回最新状态）
{"task_id": "task_1793264511_171bbcb5", "status": "running", "progress": 40, "count": 2, "error": null}

// image_download（给 LLM 的文本，图片本身不回传）
{"task_id": "task_1793264511_171bbcb5",
 "files": [{"index": 0, "path": "/workspace/images/fox_20261029_170221_0.png", "mime": "image/png", "bytes": 1496}]}
```

## 五、接入步骤

### 5.1 MCP 服务后端

1. **配置 MCP 服务**：「设置 → MCP 工具」新增服务，指向实现了本标准的 server
   （stdio 用 `command`/`args`，HTTP 用 `url`）。
2. **配置生图工具**：「设置 → 生图工具」新增配置，**后端类型选「MCP 服务」**，
   选择上一步的服务，设置默认数量 / 默认分辨率（`resolution`）/ 是否同步 / 超时，
   并勾选**工具集**：「标准三件套」与「一条龙生图」至少勾选一个，可以都勾；
   点「检测」可验证三个标准工具是否齐全，并显示参考图能力探测结果。
   「参考图能力」三态：自动（探测）/ 支持 / 不支持，探测不准时可手动钉住。
3. **挂到 Agent**：在 Mambo Agent 编辑页启用「生图工具」并选择该配置。
4. 对话中 LLM 即可调用 `image_generate` → `image_task_status` → `image_download`，
   必要时再调 `show` 展示图片。异步任务下推荐 `image_task_status(wait_timeout=30)`
   轮询，减少无效调用。

### 5.2 系统模型后端

**后端类型选「系统模型」**，从下拉里挑一个能出图的 Chat 模型（默认只列出
`meta_config.output_modalities` 含 `image` 的模型；Google / OpenAI 官方 `/models`
不返回该字段，勾选「显示全部模型」后可自行判断）。其余配置项与 MCP 后端一致；
参考图能力会按所选模型的 `input_modalities` 自动初始化（能接受图片输入 → 支持，
未声明 → 自动），并且**始终可以手动改**。详见第六节。

### 平台侧一条龙工具 `image_generate_show`

勾选「一条龙生图」后，平台额外注册一个**完全由平台实现**的工具（MCP 服务无需
感知、无需改动任何一个字），把「生成 → 等待 → 落盘 → 入库 → 展示」合并为一次调用：

| 参数 | 说明 |
|---|---|
| `prompt`（必填） | 正向提示词 |
| `resolution` | 同契约 `resolution`，缺省取配置的默认分辨率 |
| `negative_prompt` / `count` / `extra` | 同契约 |
| `reference_images` | 同契约（后端声明支持时才出现）：workspace 虚拟路径列表 |
| `mode` | 展示模式：`Normal` / `Mini_Avatar` / `Gal_Avatar` / `Group` / `Spark` |
| `path` | **可选**，落盘路径，缺省 `/workspace/images/`；**以 `/` 结尾表示目录**，否则末段视为文件名（如 `/workspace/images/fox.png` 或 `/workspace/images/fox`），目录与前缀随之推断。路径由 `VirtualPath` 校验（必须绝对、不能含 `..` / `//`、必须在 `/workspace` 之下） |
| `timeout` | 等待上限秒数，缺省取配置的等待时长（再无则 60 秒）；异步模式下即后台等待上限 |

返回 `{"status":"completed", "files":[{"index","path","mime","file_id"}], "mode"}`：
`file_id` 供前端直接渲染，`path` 留给 LLM 后续对图片做操作。若超时仍未收敛，则
**不落盘**，返回 `{"status":"running","task_id":...,"files":[]}`，LLM 可退回三件套
继续用 `image_task_status` / `image_download` 收尾。

一条龙的落盘文件名是**确定性**的：`{prefix}_{task_id}[_{index}].{ext}`（对比三件套
仍沿用下载时刻的时间戳命名，行为不变）。

#### 同步 / 异步

由配置项「默认同步等待」（`defaultSync`）决定：

| | 同步（`defaultSync=true`） | 异步（`defaultSync=false`） |
|---|---|---|
| 工具返回 | 生成完成后的 `files`（含 `file_id`） | **立即**返回 `{"status":"pending","path","paths","count","prefix","timeout"}` |
| 落盘 / 展示 | 工具内部完成 | 平台后台轮询器完成 |
| LLM 是否阻塞 | 是，最长 `timeout` 秒 | 否，一次调用即可继续 |
| 失败兜底 | 抛业务错误 | 子消息标记失败 / 超时 |

异步模式下，工具把**全部确定路径**登记为待生成文件（`pending_file_path` +
`pending_image_task_id`），平台后台轮询器发现文件尚未出现时，先按 `task_id` 驱动
一次下载落盘，再由既有的「文件出现 → 稳定性校验 → 入库 → 广播」流程展示。
因此 MCP 服务侧**同样不需要任何改动**，也无需实现阻塞等待。

> 注意：异步模式下 `timeout` 的语义是「后台最多等这么久」，不是工具阻塞时长。

#### 确定性路径的不变式（扩展名必须锁定）

异步流程是「先登记路径、后落盘」，两侧的命名必须逐字节一致：

- `path` 若给了文件名且后缀是常见图片扩展名（`.png/.jpg/.jpeg/.webp/.gif/.bmp/.tif(f)/.avif`），
  该后缀被锁定为**显式扩展名**：预测路径与落盘路径都用它（如
  `/workspace/images/凛.jpg` → `凛_{task_id}.jpg`，即便服务实际产出 `image/jpeg` 也写 `.jpg`）；
- `path` 以 `/` 结尾（纯目录）时不锁定扩展名：预测兜底 `.png`，落盘以 blob 上报的 mime 为准；
- 平台轮询器**重建落盘计划时必须沿用登记路径的后缀**，否则会写到另一个文件名上；
- 兜底：轮询器/手动获取判定「文件是否就绪」时先用精确名，未命中再用
  「同目录 + 文件名主干 + `*`」通配，因此即便扩展名或下标后缀与预测不一致
  （服务返回张数多于预测、返回格式与请求不符）也能正常入库，不会「图已落盘却判超时」；
- 去重：`pending_image_downloaded` 标记落库后，轮询器重启不会重复下载/重复入库；
  `pending_file_deadline`（epoch 秒）落库后，等待窗口也不会因重连被无限续期。

#### 等待超时 / 失败态

后台等待到期或任务失败时，子消息被标记为 `failed` 并写入 `pending_failed_reason`：

| 取值 | 含义 |
|---|---|
| `timeout` | 等待窗口到期（任务可能仍在生成） |
| `task_failed` | 生图任务失败 / 过期 |
| `no_backend` | 会话没有可用 backend 或生图配置 |
| `download_failed` | 下载 / 入库失败 |

失败态**保留** `pending_file_path` / `pending_image_task_id` / `image_run_args`，前端因此
既能展示「超时」卡片，也能提供两个入口：

```
POST /api/pending-files/{sub_message_id}/fetch
→ { status: completed | running | failed, file_id?, file_info?, error? }
```

- 手动触发一次「查任务 → 下载 → 入库」；`running` 表示任务仍在生成，稍后可再点，
  接口**不会**把子消息改回等待态，也不会重置等待窗口；
- 判定顺序改为「先看文件是否已出现、再判是否超时」，避免图已落盘却标失败；
  文件是否出现由「精确名 → 主干通配」两级判定，扩展名漂移也能命中；
- 单次 MCP `image_task_status` 调用带 20 秒上限，`wait_timeout=0` 会显式下发，
  防止服务端阻塞拖垮轮询。

## 六、内置模型后端（Chat 模型生图）

系统里已配置的部分 Chat 模型可以直接出图（Gemini 生图模型、OpenRouter 上的出图模型等）。
平台把这它们当作**第二种生图后端**，用内置实现 `ChatModelImageGenStandard` 满足同一份标准，
因此 Agent 侧的工具、`image_generate_show`、重跑、待生成文件轮询等全部逻辑完全复用。

### 6.1 绑定方式

「设置 → 生图工具」的配置项新增：

| 配置项 | 说明 |
|---|---|
| `backendType` | `mcp`（默认，原行为）/ `model`（系统模型） |
| `aiModelId` | `backendType=model` 时必填，指向 `AIModel` |
| `mcpServerId` | `backendType=mcp` 时必填（现在可为空） |
| `supportsReferenceImages` | 参考图能力三态：`null` 自动 / `true` / `false`；模型后端 `null` 按支持处理，选中模型时会按其 `input_modalities` 自动初始化，用户仍可手动改 |

其余默认参数（数量 / 分辨率 / 同步 / 等待时长 / 超时 / 工具集）与 MCP 后端共用。
模型下拉默认只列 `meta_config.output_modalities` 含 `image` 的模型，另有「显示全部模型」开关
（Google / OpenAI 官方 `/models` 不返回该字段）。

### 6.2 协议映射

只覆盖「Chat 模型通过对话接口返回图片」，**不含** `/images/generations` 这类纯生图接口。
协议按 provider 的 `worker_type` 自动推导，也可用 `extra.protocol` 覆盖：

| worker_type | 协议 | 请求 | 参考图 | 取图 |
|---|---|---|---|---|
| `google` | `google_generate_content` | `POST {apiHost}/v1beta/models/{model}:generateContent`，`generationConfig.responseModalities=["TEXT","IMAGE"]` | `parts[].inlineData` | `candidates[].content.parts[].inlineData` |
| `openai` / `deepseek` | `chat_completions` | `POST {apiHost}/chat/completions`，`modalities=["image","text"]` | `image_url`（data URL）content part | `choices[0].message.images[].image_url.url`（data URL 或 http URL） |
| `anthropic` | 不支持 | 构建配置时报错（无出图对话接口） | — | — |

与 MCP 后端的行为差异（都符合“不支持就忽略”的原则）：

- **分辨率**：Google 侧映射到最接近的 `imageConfig.aspectRatio`（1:1 / 2:3 / 3:2 / 3:4 /
  4:3 / 4:5 / 5:4 / 9:16 / 16:9 / 21:9，偏差 >3% 则忽略）；chat 协议下 `width` / `height`
  不再透传（所有网关都视为非法字段），需要精确尺寸请用 `size` / `image_config` 之类厂商字段。
- **反向提示词**：Chat 模型没有该参数，平台把 `negative_prompt` 拼进提示词尾部
  （`Avoid the following in the image: …`）。
- **`count > 1`**：拆成 N 次调用并发生成（并发上限 2），进度按完成张数上报。

### 6.3 任务与异步语义

完整实现标准的三个原语，行为与 MCP 后端一致：

- `submit`：创建任务后**立即返回** `task_id`，真正的生成在平台进程内后台跑；
  `sync=true` 时最多阻塞 90 秒（或配置的 `timeout`，取较小值），超时不取消后台任务，
  返回 `running`，符合「超时必须回落为异步」。
- 任务状态持久化在 `<storage>/image_gen_tasks/<task_id>/`（`task.json` + 图片文件），
  **不放在进程内存**，因此后台轮询器、平台重跑、进程重启后都能读到同一份结果。
- `status`：`queued` → `running`（逐张更新 `progress`）→ `completed` / `failed`；
  支持 `wait_timeout` 短轮询，状态收敛即提前返回。
  若任务停在 `queued` / `running` 且进程内已无驱动者、且超过 120 秒未更新
  （典型原因是进程重启），直接判定为 `failed` 并给出原因，避免轮询器无限等待。
- `download`：只在任务收敛后返回 `ImageBlob`（base64 + 嗅探出的 mime）。
- 单张失败会重试一次；部分成功仍返回 `completed`，失败原因记入 `errors`；全部失败才 `failed`。
- 任务目录保留 24 小时，提交新任务时顺带清理过期目录。

> 模型后端的生成是「提交即开始」，所以异步模式（`defaultSync=false`）不会减少 LLM 的等待，
> 只是把落盘 / 展示交给后台；需要真正「发完就继续」请按模型侧的自有能力评估。

### 6.4 参考图

模型后端走对话接口传图：Google 用 `inlineData`，chat 协议用 `image_url` data URL。
校验规则与 MCP 后端完全一致（8 张 / 单张 8MB / 合计 20MB / png·jpeg·webp·gif·bmp），
不满足时直接报错，不做静默裁剪。

能力默认值按模型推断：`supportsReferenceImages` 为 `null`（自动）时按「支持」处理；
在配置页选中模型时，会依据该模型的 `meta_config.input_modalities` 自动初始化
（含 `image` → 支持，声明了但不含 image → 不支持，未声明 → 自动），
**之后始终可以手动改为任意三态** —— 出图模型不必然会读图，遇到 400 就把它设成
「不支持」，参考图参数会从工具里整体消失。

## 七、图片重跑（调参重生成）与按次编组

对一张已经生成好的图片，用户可以在前端直接「重新生成 / 改参数再试一次」。
这条通道**完全由平台侧实现，不经 LLM、不改动对话历史**，因此不会破坏上下文缓存。

### 7.1 接口

```
POST /api/image-runs/{sub_message_id}/rerun
body: { prompt?, negative_prompt?, resolution?, count?, mode?, extra?, path?, timeout?, reference_images? }
```

- `sub_message_id`：目标图片子消息（任取该组里的一张即可）。
- 未传的字段沿用该「插槽」上一次生成的取值（含 `reference_images`）；`timeout` 缺省与
  agent 侧一致（生图配置的等待时长，未配置则 60 秒），上限 300 秒。
- `reference_images` 与工具侧同义（workspace 虚拟路径列表）。重跑走的是同一个标准实现，
  因此**后端不支持参考图时会直接报错**，不会静默丢弃。前端重跑面板会预填上次的取值。
- 返回 `{run_id, slot_id, status, record, files, error}`：
  - `status`：`pending`（已提交，落盘由平台后台完成）/ `completed` / `failed`
    （仅提交阶段就失败）；
  - `record`：本次生成记录子消息（`McpTool` 类型）；
  - `files`：本次产出的 FILE 子消息；`pending` 时为待生成态（`status=waiting`），
    就绪后由后台轮询器就地改成完成态。

**重跑与 agent 异步生图行为一致**：提交成功即返回，不阻塞等待、不自行下载
（否则会和后台轮询器重复取图）。落盘 / 入库 / 超时判定全部由会话级轮询器完成，
超时后子消息被标记为 `failed` 并写入 `pending_failed_reason`，前端提供「获取文件」。

### 7.2 写入的两类子消息（都不参与上下文）

| 子消息 | 说明 |
|---|---|
| **生成记录**（`McpTool` + `config.is_image_run_record`） | 记载本次下发的最终参数与结果（`status` / `task_id` / 张数 / 失败原因）。`context_participation_length=0`，且 `run_uuid` 留空。前端只在图片区域以「参数详情」打开，不进入正文工具气泡 |
| **图片**（`File`） | 本次产出的图片，`context_participation_length=0`，与首轮图片通过 `image_slot_id` 归入同一插槽。提交后先落为 `status=waiting` 的待生成文件（带 `pending_file_path` / `pending_image_task_id` / `pending_file_timeout`），由后台轮询器落盘后就地转完成态 |

### 7.3 编组字段

| 字段（`SubMessageConfig`） | 含义 |
|---|---|
| `image_run_id` | 本次生成 run 的标识：LLM 调用取该工具的 `tool_call_id`，平台重跑取新生成的 uuid |
| `image_slot_id` | 所属「插槽」：同一位置的第 1/2/3 次生成共享；为空表示自成一插槽 |
| `image_run_args` | 本次生成下发的参数快照（前端用于预填参数面板与摘要展示） |
| `image_pinned_run_id` | 用户当前置顶的 run（只写在插槽内最早的一条图片子消息上） |
| `is_image_run_record` | 标记「生成记录」子消息 |

首轮由 LLM 调用时，平台会自动把 `image_run_id` / `image_run_args` 写进图片子消息；
更早的历史数据没有这些字段，前端会用「工具结果里的 `file_id` → `tool_call_id`」反查补齐。

### 7.4 展示规则

- 同一插槽下的多个 run 用左右箭头切换置顶；run 内的多张图用缩略图条切换。
- 只有 `Normal` / `Group` 两种展示形态进入该区域；`Mini_Avatar` / `Gal_Avatar` /
  `Spark` 仍按原有规则渲染。
- 仅有单张图且来源不是 `image_generate_show` 的图片（例如手工 `show`）不进入该区域，
  保持原有正文渲染。
- **等待中 / 超时失败**的图片子消息同样归入该区域（按 `image_run_id` 归组，不要求
  `file_info`），失败 run 在区域内展示原因并提供「获取文件」与「重新生成」；
  非画廊形态（`Mini_Avatar` / `Gal_Avatar` / `Spark`）由正文的文件卡片兜底展示失败态。

## 八、参考实现

`MCP_SERVER/image_gen_standard_server.py` —— 无第三方依赖的合规示例：

- 生成纯色占位 PNG（标准库 zlib + struct 手写 PNG 编码）；
- 任务状态落 `%TEMP%/mambo_image_gen_standard/tasks.json`，stdio 重启不丢；
- 支持透传 `extra`：`width` / `height` / `color`(r,g,b) / `fail`；
- 支持 `resolution` 分辨率（`1024x1024` 等，低于显式 `width`/`height` 优先级）；
- 支持 `reference_images`（`list[mcp.types.ImageContent]`）：张数 / mime / base64 /
  体积严格校验，非法即报错；占位色按首张参考图的摘要微调，证明图确实被消费；
- `image_task_status` 实现 `wait_timeout` 阻塞轮询，状态收敛即提前返回。

```json
{
  "command": "<项目 runtime/python/python.exe 的绝对路径>",
  "args": ["<项目绝对路径>/MCP_SERVER/image_gen_standard_server.py"]
}
```
