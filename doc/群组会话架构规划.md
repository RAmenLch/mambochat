# 群组会话架构规划

> 状态：架构与文件级实施规划，尚未实现业务代码。
> 本文根据现有会话模型、生成入口、工具组装链、前端会话树和用户已确认的产品规则整理。
> 下文中字段名、接口名及新增文件名为拟定设计，不表示当前项目已经具备这些能力。用户已确认的需求与本轮补充设计建议分开标注。

## 1. 目标与已确认规则

1. 群组是会话表中的特殊文件夹，包含 N 个普通 Agent 子会话，N > 2。
2. 同一 Agent 可以重复选择；每个成员拥有独立子会话、上下文及自定义别名。
3. 邮箱地址就是成员别名：`address[] = MemberName[]`，不是 UUID、外部邮箱或 SMTP 地址。
4. 串行范围仅限同一个群组。不同群组、群外普通会话不受该群锁限制。
5. 群组提供 `memberList()`、`sendMail(address[], title, content)`、`readMails()`。
6. 生成开始时冻结可读邮件；同轮读取内容保持一致；生成期间新邮件下一轮可见。
7. `sendMail` 仅暂存。**自动模式**下只有生成正常完成后才真正投递；**审核模式**下轮次结束后邮件进入待审核，由用户逐封「同意 / 拒绝（必须填原因）」后才投递。停止、失败不投递；等待工具审核、等待用户回答、等待邮件审核都会暂停整个群组。
8. 邮件投递后自动触发收件成员，用户消息为 `[system messages] 存在未读邮件`。
9. 实际调用 `readMails` 且正常完成后才确认快照邮件已读。未读取时保持未读，但不无限自动重试。
10. 用户无 `@` 的输入广播给全部成员；多个 `@` 分别发送到被选中的子会话。
11. 邮件格式中的成员列表表示本邮件全部收件成员，让收件人知道其他哪些成员也收到了内容。允许增加发件人字段。
12. 首版固定成员、共享原 Agent 配置、提供自动轮次上限。
13. 优先复用现有生成、消息、工具展示及会话树，避免改写模型适配器或 Agent 执行框架。

### 1.1 首版补充建议

这些是本轮为了消除实施歧义提出的建议，不冒充用户已逐项确认的规则：

- 创建时自定义别名；首版创建后固定别名及 Agent 绑定，暂不提供成员改名/增删/换绑。
- 别名进行首尾去空白和 Unicode NFC 规范化，限制为 1～64 字符；拒绝控制字符、换行、`@` 和英文逗号。允许中文和内部空格，使用结构化提及避免解析歧义。规范化后区分大小写匹配。
- 群内别名唯一，群间允许重复；别名不是会话标题，标题改变不改变地址。
- 允许向自己发信，但同样延迟投递、下一轮处理，并受自动轮次上限约束。
- 自动轮次上限建议默认 50，可配置为正整数；**以「一次发起沟通」为额度周期**：用户新发消息（群输入，或在成员子会话里直接发言）即开启新周期并把已用轮次清零，周期内按自动邮件任务实际启动次数累计（按成员任务计，一次群内往返在 N 人群里最多消耗 N 次）。暂停/恢复、重试、重新生成、编辑重发、工具审核与 ask_user 恢复都不会偷偷重置，只有用户新发起或明确重置才清零。达到上限时暂停整群并保留队列与未读邮件，用户可重置后继续、放弃该轮或停止。
- 首版群组输入框仅发送文本；子会话保留现有附件输入。群组输入未来可通过复用 GenerateRequest 扩展。
- 非正常结束后暂停群组，用户选择恢复该轮、放弃该轮后继续，或停止处理，避免失败后悄悄产生更多副作用。
- 首版基于现有内存 StreamManager 的单后端进程部署，不宣称支持多进程协调生成；需要多进程时另行设计租约、心跳和 fencing token。

## 2. 现状与约束

| 已核对的现有代码 | 当前能力及约束 |
| --- | --- |
| `backend/models/chat_model.py` | Chat 共用会话/文件夹模型，itemType 为 chat/folder，parentId 组织树，agentId 无唯一约束；没有成员别名和群标记。 |
| `backend/crud/chat_crud.py` | create_chat、update_chat 等内部 commit；不能循环调用 create_chat 来实现整组原子创建。 |
| `backend/routers/chat_management.py` | 会话默认模型、参数校验和资源校验主要在路由；需要窄范围抽取复用。 |
| `backend/routers/chat_interaction.py` | 新生成、编辑重发、重生成、重试、工具审核恢复、ask_user 恢复均在这里接入。 |
| `backend/services/stream_manager_service.py` | 内存消息订阅和按 chatId 的生成锁；没有跨成员群锁和持久化队列。 |
| `backend/services/generation_service.py` | 统一托管生成与重试，但取消也可能使用 COMPLETED 收尾，不可据此判断邮件发送成功条件。 |
| `backend/services/generation/managers/default_manager.py` | 审核中断与正常结束有区别；异常 finish_reason 可能显示错误但消息仍使用 COMPLETED，需要独立的业务结束结果。 |
| `backend/services/generation/builders/director.py` | 各 Agent initializer 已支持 external_tools，适合注入群工具；还须接入 provider、提示词和恢复展示，不能只拼接工具列表。 |
| `backend/alembic/env.py` | 显式导入模型，新增模型必须注册到迁移 metadata。 |
| 前端 chatSessionStore / ChatList | 普通 folder 不可进入会话页面，currentChat 只返回 chat；不能简单将所有 folder 当成聊天。 |

现有 Agent 模型配置是共享的。重复选择 Agent 不等于复制配置，修改该 Agent 会影响所有引用它的成员。成员的邮箱和会话身份必须独立于 Agent.name。

## 3. 总体架构

```text
群组特殊文件夹 Chat
  ├─ 成员子会话 Chat A → Agent X，memberAlias=分析员
  ├─ 成员子会话 Chat B → Agent X，memberAlias=质疑者
  └─ 成员子会话 Chat C → Agent Y，memberAlias=总结者

群页面输入 / 成员子会话操作 / 邮件投递
                  ↓
          持久化 GroupTask 队列
                  ↓
          GroupScheduler 群内串行
                  ↓
       GenerationBridge → 现有生成服务
                  ↓
      GroupMailToolProvider（固定轮次上下文）
                  ↓
       正常结束 → 单事务确认读取/投递
                  ↓
       群邮件流更新 + 收件人成员任务入队
```

职责边界：

- 群组父节点只承载组织结构和群页面，不拥有普通 LLM 历史。
- 成员子会话复用现有 Message/SubMessage、Agent、checkpoint 和流式输出。
- 邮件是独立业务实体，不从工具调用文本临时拼装群记录。
- 队列和邮箱状态由后端负责；浏览器只发命令、展示及订阅更新。
- `GroupTask` 同时承担排队命令和逻辑生成轮次，首版不额外拆分 job/run 两套表。
- 工具接口地址始终是别名；内部子会话 ID 只用于可靠关联、权限校验、索引和身份去重，不暴露为另一套邮箱地址。

## 4. 数据结构规划

### 4.1 修改 Chat：只增加两个持久化字段

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `folderType` | String(20), nullable | 普通节点为空；群组父节点为 `group`，且 itemType 必须为 folder。 |
| `memberAlias` | String(64), nullable | 群组成员的邮箱地址/别名；非成员为空。 |

群父节点：`itemType=folder, folderType=group, memberAlias=null`。

成员子节点：`itemType=chat, chatMode=agent, parentId=groupId, agentId=选中Agent, memberAlias=别名, folderType=null`。

约束：

- 唯一索引 `(parentId, memberAlias)`；普通节点 alias 为 NULL，不影响同名普通会话。
- 不新增 Agent 唯一约束；重复 Agent 必须合法。
- 仅群成员可设置 memberAlias；仅 group folder 的直接子节点是成员。跨表约束由统一服务检查。
- 复用 parentId 表达成员归属，不再增加易失配的持久化 groupId。API 可提供派生的 `groupId`。
- 保留 Chat.name 作为会话标题；创建时可初始化为别名，但以后两者不能隐式互改。
- 普通 ChatCreate/ChatUpdate 不允许客户端任意写群标记/别名；由专用创建接口管理。

### 4.2 新表 GroupState：群组运行状态

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `groupId` | UUID，主键，关联 Chat.id | 必须指向 group folder。 |
| `status` | ready / paused / deleting | 可调度、暂停、正在删除。等待审核等具体原因由 pauseReason 表示。 |
| `pauseReason` | nullable String | manual、review、ask_user、failure、cancelled、restart、round_limit 等。 |
| `activeTaskId` | nullable UUID | 当前逻辑轮次；等待审核时仍保留，不代表有线程持续执行。 |
| `autoRoundLimit` | 正整数 | 自动邮件轮次上限，建议默认 50。 |
| `autoRoundCount` | Integer，默认 0 | **本次发起沟通的额度周期内**已启动的自动邮件逻辑轮次数；用户新发起新一轮对话或显式重置时清零，同轮恢复不重复增加。 |
| `mailMode` | auto / review，默认 auto | 邮件投递模式：auto=轮次正常结束后自动投递；review=轮次结束后邮件待用户逐封审核。切换只影响之后的轮次，已在待审核的批次仍由用户决定。 |
| `totalAutoRoundCount` | Integer，默认 0（派生值） | 群累计实际启动过的自动邮件轮次（跨额度周期，仅用于展示；由 GroupTask 统计得出，不落库）。 |
| `nextTaskSeq` | Integer | 分配群内 FIFO 队列序号。 |
| `nextMailSeq` | Integer | 分配已投递邮件的严格展示顺序。 |
| `version` | Integer | 乐观并发版本及前端通知对账版本。 |
| `createdAt / updatedAt` | DateTime | 使用项目统一时间配置。 |

activeTaskId 用应用层校验关联 GroupTask，避免循环级联关系；抢占须在短事务中按状态/version 条件更新，不能只依赖内存标志。

### 4.3 新表 GroupTask：排队命令 + 逻辑轮次

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | UUID 主键 | 也是邮件暂存和收件快照的轮次标识。 |
| `groupId / memberChatId` | UUID，索引 | 所属群和执行成员。 |
| `sequence` | Integer | 群内 FIFO 顺序，唯一 `(groupId, sequence)`。 |
| `kind` | user_message / mail_notice / regenerate / edit_regenerate | 重试和审核继续恢复原轮次，不创建新的业务轮次。 |
| `state` | queued / running / waiting_review / waiting_user / ready_to_commit / succeeded / failed / cancelled / interrupted / skipped | 明确区分业务成功与消息展示状态。 |
| `requestId` | String，nullable | 用户命令幂等键；广播同一 requestId 对多个成员各建一项。唯一 `(groupId, requestId, memberChatId)`，NULL 不用于幂等。 |
| `payload` | JSON | 完整输入副本、附件引用（子会话入口）、编辑内容、目标消息等；不得仅引用前端草稿。 |
| `baseMessageId / userMessageId / assistantMessageId` | nullable UUID | 对接现有消息。删除历史后保留溯源 ID，不对这些字段配置级联删除任务。 |
| `coalesceKey` | nullable String，唯一 | 等待中的邮件任务为 `groupId:memberChatId`；离开 queued 后清空，允许该成员再排一次后续任务。 |
| `snapshotReceiptIds` | JSON 数组 | 首次启动时冻结的收件记录 ID，恢复原轮次时不重取。 |
| `snapshotTakenAt` | nullable DateTime | 区分尚未冻结与冻结结果为空。 |
| `mailReadRequested` | Boolean，默认 false | 本轮是否实际调用 readMails；不是冻结即已读。 |
| `attemptCount` | Integer | 原轮次恢复次数，用于排查而非自动无限重试。 |
| `startedAt / finishedAt / createdAt` | DateTime | 生命周期记录。 |
| `errorCode / errorMessage` | nullable | 可显示的失败原因，不保存密钥等敏感配置。 |

设计说明：

- 每个任务最多关联一个逻辑 assistant message；恢复使用已有 ID，不重复写通知消息。
- 只在轮到执行时生成用户消息和 assistant 占位，排队阶段不改变子会话活跃路径。
- 消息准备需提供“不自行 commit”的窄入口，使任务绑定与消息创建在一个事务中完成；不能重启后因关联未写入而重复创建消息。
- `snapshotReceiptIds` 对应的邮件内容与收件人快照提交后不可变，因此无需为快照重复复制全部正文。
- 同轮失败恢复保持快照和待发箱；完整重新生成属于新 task，旧 task 待发箱不得继承。

### 4.4 新表 GroupMail：待发箱与已发送邮件共用实体

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | UUID 主键 | 一封邮件。 |
| `groupId / sourceTaskId` | UUID，索引 | 群组和发送轮次。 |
| `senderChatId` | UUID | 发送成员身份，由服务端绑定，模型不能指定。 |
| `senderAliasSnapshot` | String | 发件时别名。 |
| `recipientSnapshot` | JSON 数组 | `[{memberChatId, memberName}]`，保留规范化去重后的完整收件列表及顺序。 |
| `title / content` | String / TEXT | 邮件标题、正文。长度上限在 Schema 中统一规定。 |
| `toolCallId` | String | 工具调用标识，唯一 `(sourceTaskId, toolCallId)`。 |
| `toolCallOrder` | Integer | 本轮工具调用的稳定顺序，不按工具并发完成时间排序。 |
| `state` | staged / reviewing / deferred / sent / rejected / discarded | 暂存、待用户审核、已同意但因同批存在拒绝而暂缓投递、已投递、已拒绝、放弃；失败时先保留 staged 供原轮次恢复。 |
| `reviewedAt` | datetime，可为空 | 用户审核时间（同意或拒绝）。 |
| `rejectReason` | text，可为空 | 拒绝原因，拒绝时必填，会转述给发信人。 |
| `sequence` | nullable Integer | 真正投递时分配，唯一 `(groupId, sequence)`。 |
| `createdAt / sentAt` | DateTime | 暂存时间、实际投递时间。 |

- staged 不向收件人和群公共邮件流暴露，不生成收件记录，不触发任务。
- 同一次工具调用重放返回同一暂存邮件；同 key 却参数不同则报幂等冲突，不覆盖原文。
- 相同正文的两个不同工具调用仍可产生两封邮件，不能按正文粗暴去重。
- 一封邮件发给多人，群页面仍只展示一封。

### 4.5 新表 GroupMailReceipt：每位成员独立收件状态

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | UUID 主键 | 可被轮次快照引用。 |
| `mailId` | UUID | 已发送邮件。 |
| `recipientChatId` | UUID | 收件成员。唯一 `(mailId, recipientChatId)`。 |
| `readAt` | nullable DateTime | NULL 为未读。 |
| `readByTaskId` | nullable UUID | 哪轮正常完成后确认读取。 |
| `notificationTaskId` | nullable UUID | 此收件记录已登记到哪个自动任务，避免“仍未读”造成无限通知。 |
| `createdAt` | DateTime | 投递时间。 |

索引至少包含 `(recipientChatId, readAt)`、mailId、notificationTaskId。

### 4.6 删除与迁移

- 新增字段对旧记录均为 NULL，旧会话与文件夹行为不变；不转换已有历史。
- 新表由 Alembic 创建，并注册模型；SQLite 的唯一索引和迁移批处理按项目方式处理。
- 当前连接配置未显式启用 `PRAGMA foreign_keys=ON`，不能仅依赖 ForeignKey 声明保证级联或结构完整；本方案不为此贸然修改全局数据库行为。
- 群组删除统一走服务：禁止新入队 → 等待/停止当前执行并确认退出 → 删除 receipts、mails、tasks、state → 删除群及成员 Chat；处理引用 checkpoint 的既有清理流程。
- 删除普通父文件夹时也须先识别其后代群组，不能绕过上述清理。
- 不允许删除单个成员、复制成员到群内、在群内新建普通节点、移入移出成员或换绑 Agent。群组整体可移动到普通文件夹，禁止群组嵌套群组。
- 被群成员引用的 Agent 或其祖先文件夹删除应被阻止并返回引用提示；避免固定成员失效。存量异常引用仍须在执行前检测并暂停，不自动降级成普通会话。
- 回滚迁移会删除群业务数据，必须先备份；不承诺老版本能理解或继续运行群任务。

## 5. 工具契约与隔离

### 5.1 memberList()

返回当前群组的成员列表，例如：

```json
[
  {"address": "分析员", "memberName": "分析员", "description": "负责分析问题"},
  {"address": "质疑者", "memberName": "质疑者", "description": "负责分析问题"},
  {"address": "总结者", "memberName": "总结者", "description": "负责整理结论"}
]
```

简介默认取当前 Agent.description。重复 Agent 可有相同简介，但地址必须不同。不能列出别的群组或普通会话。

### 5.2 sendMail(address[], title, content)

- address 是非空 MemberName 数组，仅接受当前群规范化后存在的别名。
- 去重保留顺序；任一地址无效则整封拒绝，不部分发送。
- 服务端将别名解析成 memberChatId，同时保存完整别名快照。
- 只写 staged 邮件，返回 mailId 与结果说明：自动模式为“已加入本轮待发箱，将在本轮正常结束后投递”；审核模式为“已提交用户审核，用户同意后才会投递”。
- 工具所属 groupId、memberChatId、taskId 和 toolCallId 由受信任运行上下文提供，不是可被模型伪造的参数。
- 工具允许在同轮被多次调用。并行工具调用使用独立 DB session/短事务，不能跨并行调用共享 AsyncSession。

### 5.3 readMails()

- 首次启动 task 时冻结全部已投递未读 receipt；不是首次调用工具时才冻结。
- 每次只读取 snapshotReceiptIds，按 mail.sequence 输出；本轮重复调用结果一致。
- 调用时记录 mailReadRequested=true；实际 readAt 在正常完成事务中更新。
- 无邮件时返回明确的“本轮没有未读邮件”，不触发额外任务。
- 返回格式：

```markdown
## $标题
### 发件人
$SenderMemberName
### 本邮件发送的群成员列表
$Member1,$Member2,$Member3
### 内容
xxxxxxx
```

多封依次拼接；收件列表包含自己和其他收件成员，是发件时快照，不是当前已读成员列表。

### 5.4 运行上下文

新增轻量 GroupExecutionContext，至少包含 taskId、groupId、memberChatId、memberAlias、assistantMessageId。由调度器显式传入托管生成和 Director，不通过 Agent 全局配置或进程可变全局变量传递。

仅在群成员主对话轮次注入三个工具和操作提示；不注入标题生成、历史压缩、群外会话。Agent 内部 task/subagent 不成为群成员，默认不继承邮箱工具；需要核查各 builder 的工具传递，防止间接使用别人的成员身份。

邮件正文是成员提供的数据，不作为受信任系统指令。`@私聊` 只隔离初始输入，不能保证 Agent 不主动将内容转发给其他成员。

## 6. 调度、事务与恢复

### 6.1 唯一调度入口

所有群成员操作先识别 parentId 对应的群：新消息、编辑重发、重生成、checkpoint 重试、审核继续和 ask_user 继续均经过 GroupGenerationBridge。群外继续旧流程。

群内串行按“成员主对话逻辑轮次”定义；内部工具并行不等于另一个成员会话在生成。辅助标题不持有群成员轮次，也不能读取/发送邮件。手动历史压缩、分支切换、删除/编辑历史会改变上下文，应在有关成员有排队/活动任务时禁止，不能与该轮并行修改。

### 6.2 入队

1. 验证群、成员、别名、Agent 可用性与输入。
2. 用户群输入一次事务创建所有目标成员的 user_message tasks；无 @ 为全部成员，多 @ 去重后为指定成员。
3. 同批收件成员按当前成员 sortOrder、id 排序入队，后续各命令按 sequence FIFO。
4. 邮件入队使用唯一 coalesceKey 合并“尚未运行”的同一成员通知，已在运行的成员最多再排一个待执行邮件任务。
5. requestId 对网络重发幂等；重试请求携带相同 key 和不同 payload 时拒绝，不默默覆盖。
6. 入队失败不改变用户草稿、不创建半批任务。

### 6.3 开始执行与冻结

1. 调度器在 GroupState 可运行且无活动轮次时选择最早 queued task。
2. 短事务抢占 activeTaskId，清理其 coalesceKey，冻结 receipts，并将任务准备所需状态持久化。
3. 若 mail_notice 轮到执行时已无未读邮件（被前一个用户轮次读取），标记 skipped，不写空通知、不调用模型、不计自动轮次。
4. 在受控事务中创建/绑定 user message 和 assistant 占位；邮件任务只写一次指定用户提示。
5. 取得既有 chatId 生成锁，调用现有生成服务；邮件快照与模型调用不共享长数据库事务。
6. 等待审核/用户回答时释放物理执行资源但保留 activeTaskId、快照和暂存邮件，群状态暂停；其他成员不继续。

生成中对该成员新增的用户输入只排队，不立刻修改正在运行的子会话历史。

### 6.4 正常结束提交

现有生成服务输出独立 GenerationOutcome：normal_completed、cancelled、failed、waiting_review、waiting_user。normal_completed 必须表示完整执行链完成（包括正常尾部工具），没有取消、异常结束或待审核，不能直接等同 MessageStatus.COMPLETED。

1. 将任务标记 ready_to_commit，保存明确的正常结束事实；若此持久化前进程退出，保守视为 interrupted，不猜测成功。
2. 一个邮箱事务中：
   - 检查 task 尚未 succeeded；重复完成回调只返回已有结果。
   - 若 mailReadRequested，则仅将 snapshotReceiptIds 对应未读记录确认已读。
   - 按 toolCallOrder 提交 staged 邮件，分配群 mail sequence。
   - 为所有收件人创建独立 receipt。
   - 创建或合并收件人的 queued mail_notice，绑定 notificationTaskId。
   - 更新 task=succeeded，清理 activeTaskId，更新群 version。
3. 提交后发全局通知，唤醒调度器。通知丢失不影响已落库结果，可通过详情接口对账。

ready_to_commit 崩溃恢复只重试邮箱事务，不重新调用模型。该设计保证“数据库投递一次”，不宣称模型执行或所有外部工具副作用恰好一次。

### 6.5 停止、失败、审核与恢复

| 情况 | 邮件与快照 | 群调度 |
| --- | --- | --- |
| 正常完成 | 投递 staged；实际读取过才确认已读 | 执行下一 queued |
| 工具审核 / ask_user | 保留 staged 和原快照，不投递不确认 | 暂停整群；只允许该 activeTask 的合法继续 |
| 异常/截断/用户停止 | 不投递，不确认；保留暂存和诊断信息 | 暂停，等待用户选择恢复或放弃 |
| 恢复同轮 | 原 task、原快照、原 assistant/checkpoint；sendMail 按 toolCallId 去重 | 不重新计自动轮次 |
| 放弃该轮 | staged → discarded；未读保留 | 清理活动轮次，用户确认后继续后续任务 |
| 完整重生成 | 新 task、新快照；不继承旧轮次暂存箱 | 已发送邮件不撤回，新轮次可能产生新的邮件，UI 提醒 |
| 后端重启 | running → interrupted；ready_to_commit 可仅恢复提交；待审核保留 | 受影响群暂停，queued 保留，不自动重放有副作用的生成 |

暂停群组默认是不再启动下一轮，当前正在运行的轮次允许正常结束；“停止当前轮次”是独立操作，会取消且不投递。达到上限时仍接受入队，但停止自动执行并提示，不丢邮件。

失败后选择放弃而非恢复时，不清空 notificationTaskId 去制造自动重试；未读邮件可由后续新来信触发的轮次或明确“处理未读”操作读取。

### 6.6 防止无限通知

- 只对新投递产生的 receipt 登记自动通知，不以“收件箱仍有未读”作为无条件循环调度依据。
- 模型未调用 readMails 便正常完成：邮件保持未读，UI 显示未处理，不为这批旧邮件重复建立任务。
- 后续新邮件到达可以触发新任务，其快照包含仍未读的旧邮件和新邮件。
- 即使群组整体串行导致成员邮件通常在轮次边界投递，仍保留固定快照协议，并通过服务级验收模拟运行中新增来信。

## 7. HTTP 接口与通知规划

以下使用 `/api/group-chats` 作为新路由命名空间，最终编码时与现有命名规范统一。

| 接口 | 职责 |
| --- | --- |
| `POST /group-chats` | 原子创建群父节点、GroupState 和 N 个成员；返回群与完整子节点，避免新文件夹缓存误判为空。 |
| `GET /group-chats/{groupId}` | 群元信息、成员、运行状态、版本、未读/未处理摘要。 |
| `GET /group-chats/{groupId}/mails?afterSequence=...&limit=...` | 按 sequence 游标分页获取 sent 邮件。 |
| `GET /group-chats/{groupId}/mail-reviews` | 审核模式：待审核邮件 + 已决策邮件（被拒 / 已同意待投递）。 |
| `POST /group-chats/{groupId}/mails/{mailId}/approve` | 审核模式：同意投递该邮件；同批末封处理完即定稿（无拒绝则立即投递）。 |
| `POST /group-chats/{groupId}/mails/{mailId}/reject` | 审核模式：拒绝投递该邮件，reason 必填；同批末封处理完定稿并通知发信人。 |
| `GET /group-chats/{groupId}/tasks?...` | 当前及排队任务、终态历史分页；私聊正文非公共邮件流。 |
| `POST /group-chats/{groupId}/messages` | 接收 requestId、content、recipientNames；空数组明确表示广播，非空逐别名验证并排队。 |
| `POST /group-chats/{groupId}/pause` | 暂停后续调度，不等同取消当前生成。 |
| `POST /group-chats/{groupId}/resume` | 恢复可继续群；待审核/失败不能被普通 resume 越过。 |
| `PATCH /group-chats/{groupId}/settings` | 修改自动轮次上限；显式请求才能重置计数（resetAutoRoundCount 会清零本次额度周期，并在 pauseReason=round_limit 时一并解除暂停）。 |
| `POST /group-chats/{groupId}/tasks/{taskId}/retry` | 恢复允许恢复的原轮次，不创建重复通知。 |
| `POST /group-chats/{groupId}/tasks/{taskId}/cancel` | 取消 queued 或停止 running；按状态幂等处理。 |
| `POST /group-chats/{groupId}/tasks/{taskId}/discard` | 放弃失败/停止/中断轮次，丢弃待发箱，不撤回已发送邮件。 |
| `POST /group-chats/{groupId}/members/{memberChatId}/process-unread` | 用户明确要求处理遗留未读，复用合并队列。 |
| `DELETE /group-chats/{groupId}` | 生命周期感知的整组删除。普通删除入口也必须委托同一服务。 |

创建请求示例：

```json
{
  "name": "方案讨论组",
  "parentId": null,
  "autoRoundLimit": 50,
  "members": [
    {"agentId": "agent-A", "memberAlias": "分析员"},
    {"agentId": "agent-A", "memberAlias": "质疑者"},
    {"agentId": "agent-B", "memberAlias": "总结者"}
  ]
}
```

### 7.1 子会话接口兼容策略

现有生成端点对群外保持旧响应。群成员新输入/重生成/编辑重发采用可判别的排队响应，例如 `kind=group_task, taskId, groupId, state=queued`；前端不得将 queued 当作已经有 assistant message 或已经可订阅的流。

建议统一扩展 Schema 为旧结果与 GroupTaskAccepted 的联合类型，并在 chatInteractionStore 单点处理。待任务实际启动，群通知携带 chatId、assistantMessageId、taskId，只有当前打开的该子会话恢复普通流订阅。

审核/ask_user 仍提交现有决策结构，但恢复须核对 activeTaskId 和轮次状态，不能直接调用后台生成绕过调度。重复批准/恢复只能启动一次。

### 7.2 通知

复用全局通知通道，增加：`group_created`、`group_state_changed`、`group_task_changed`、`group_mail_sent`、`group_deleted`。

事件包含 groupId、version、taskId/mailId 及必要路由信息。邮件正文通过分页接口取得，不在所有全局事件中重复广播。重连后主动读取版本和缺失邮件；SSE 关闭只是连接状态，不是生成正常完成信号。

| `i18n/locales/zh-CN/common.ts`、`i18n/locales/en/common.ts` | 错误码、别名冲突、固定成员、群暂停及输入失败提示。 |

### 9.3 前端全部生成/恢复交互覆盖

不能只给群输入框增加 busy 状态。下列位置统一使用 chatInteractionStore 的群任务结果及能力判断：

| 现有文件 | 操作 |
| --- | --- |
| `components/chat/ChatWindow.vue`、`mobile/components/chat/ChatWindow.vue` | 发送、停止、草稿保留、桌面复制到此处限制。 |
| `components/chat/MessageItem.vue`、`mobile/components/chat/MessageItem.vue` | 重新生成、编辑后重发。 |
| `components/chat/dialogs/MessageEditDialog.vue`、`mobile/components/chat/dialogs/MobileMessageEditDialog.vue` | 编辑/重发准入；移动端补齐能力控制。 |
| `components/chat/message/MessageActions.vue` | 分支、重生成、复制/删除能力。 |
| `components/chat/message/AssistantBubble.vue` | 失败 checkpoint 重试。 |
| `mobile/components/chat/message/MobileAssistantBubble.vue` | 群重试入口可与群面板复用；若要求普通气泡操作两端一致则补齐。 |
| `components/chat/dialogs/McpToolDialog.vue`、`mobile/components/chat/dialogs/MobileToolDialog.vue` | 批准、编辑批准、拒绝后的同轮恢复。 |
| `components/chat/dialogs/AskUserDialog.vue`、`mobile/components/chat/dialogs/MobileAskUserDialog.vue` | 用户回答后的同轮恢复。 |

普通新输入允许排队，不应因 groupBusy 一律拒绝；历史修改类操作需要防冲突。等待审核时必须允许当前活动 task 合法继续，不能被通用禁用逻辑误锁死。

### 9.4 明确优先不改的部分

- `components/common/ExplorerTree.vue`：利用已有节点点击、插槽及 customAllowDrop。
- `utils/treeHelper.ts`：群仍是 folder，复用原构树。

- `composables/useTreeStoreActions.ts`：避免走“新建 folder 默认已加载且为空”的假设，群结果在 chatListStore 单独合并。
- `router/index.ts`：保留 `/chat/:chatId?`；修正两端列表读取 `route.params.id` 的接入问题，不新增重复路由。
- 通用 SSE 传输、LLM provider adapter、worker 解码、Agent 全局模型、普通 Message/SubMessage 格式原则上不改。

## 10. 实施阶段与交付物

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A. 数据与创建 | 迁移、模型、Schema、创建 API、结构保护 | 旧数据兼容，N 校验、重复 Agent、别名约束、创建回滚可验收。 |
| B. 邮箱核心 | 暂存、固定快照、收件状态、幂等提交 | 无须接真实模型即可用服务调用验证读写和事务语义。 |
| C. 群调度 | 持久化任务、群锁、上限、恢复 | 同群串行、跨群独立、审核暂停、异常和崩溃恢复可验收。 |
| D. 生成接入 | 工具 provider、outcome、所有入口适配 | 原 Agent 链可使用三工具，只有正常完成后投递。 |
| E. 前端 | 创建表单、群页、@ 输入、邮件流、两端接入 | 排队状态、草稿保护、子会话导航与回连正确。 |

不拆成“先做能跑的前端队列，再补可靠性”。固定快照、明确 outcome、后台队列、幂等提交是基础正确性，应在首版一并成立。

## 11. 验收标准

### 11.1 数据与结构

- AC-01：N=2 创建失败，N=3 成功；同一 Agent 选择 3 次合法，生成 3 个独立子会话。
- AC-02：规范化后同群重复别名失败；不同群相同别名合法；address 与 memberAlias 完全一致。
- AC-03：任一成员创建失败，父文件夹、GroupState 和所有子会话都不残留。
- AC-04：普通重命名/自动标题不修改邮箱地址；Agent 名称修改不修改成员别名。
- AC-05：普通拖拽、PUT parentId、reorder、新建、复制、归档、换绑不能绕过固定成员限制。
- AC-06：群或包含群的祖先文件夹删除不会留下队列、邮件或仍在执行的成员；被引用 Agent 删除得到明确提示。

### 11.2 工具和邮件

- AC-07：memberList 只列当前群成员别名地址与简介；重复 Agent 的成员可区分。
- AC-08：sendMail 使用 MemberName[]；空收件人、无效或跨群地址整封拒绝；重复地址只收一次。
- AC-09：工具调用后邮件仍为 staged，收件人读不到、群邮件流不出现、不触发生成。
- AC-10：正常结束后统一投递，群邮件流每封只显示一次；多个收件人各有独立 readAt。
- AC-11：格式含标题、发件人、全部收件别名和正文；成员列表不是已读列表。
- AC-12：一轮反复 readMails 的文本和顺序完全一致；服务级模拟轮中来信时，新信下一轮才出现。
- AC-13：未调用 readMails 正常结束仍未读，且旧邮件不无限触发；新邮件可再次触发并带上旧未读。
- AC-14：确认已读只影响原 snapshot，不把生成中新增邮件误标已读。

### 11.3 队列与输入

- AC-15：群页、子会话页、多个客户端同时提交，单群最多一个成员执行；不同群可以独立运行。
- AC-16：批量来信给尚未执行成员合并成一个 queued 邮件任务；正在执行成员最多再有一个 queued 邮件任务。
- AC-17：邮件实际执行时只写一次指定 User 提示；任务启动前已无未读则 skipped、不调用模型。
- AC-18：无 @ 输入分别进入全部子会话；多 @ 只进入选中成员；同名 Agent 不造成错投。
- AC-19：生成中提交的私聊排队且不修改当前生成历史；网络重发不重复创建任务。
- AC-20：私聊内容不进入其他成员上下文或群公共邮件流；Agent 主动转述不被错误宣传为无法发生。
- AC-21：排队或发送失败有明确结果；失败保留草稿；切换页面后旧流不覆盖新会话。

### 11.4 停止与恢复

- AC-22：用户停止、异常 finish_reason、执行失败均不提交待发邮件、不确认已读。
- AC-23：审核和 ask_user 暂停整群，快照不变；恢复原 task，不新增通知、不重复计自动轮次。
- AC-24：同工具调用重放、重复完成回调、HTTP 重发不造成重复投递；同 key 不同内容被拒绝。
- AC-25：ready_to_commit 崩溃恢复只提交邮箱，不重新调用模型；提交事务中失败全部回滚。
- AC-26：running 时重启标记 interrupted 并暂停，queued 不丢失，不自动重放外部工具。
- AC-27：完整重生成创建新轮次；旧已发邮件不撤回；UI 明确提示可能产生新投递。
- AC-28：达到本次发起沟通的自动轮次上限时暂停整群且保留队列；恢复不会暗中清零；用户新发起新一轮对话或显式重置才清零（因 round_limit 暂停时，重置会一并解除该暂停以继续执行）。

### 11.5 页面与兼容

- AC-29：群创建后可展开看到全部成员，群页可打开；刷新深链接、桌面/Electron 和移动端恢复路径正确。
- AC-30：邮件按 sequence 分页，刷新与通知重连后不缺失、不重复、不重排。
- AC-31：群外普通会话不注入邮箱工具、不进入群队列，普通文件夹仍只展开。
- AC-32：成员继承原 Agent 工具和配置；共享配置有提示；内部 subagent、标题、历史压缩不能冒充成员收发邮件。
- AC-33：群组不伪装支持旧导出格式；不支持的复制/导入导出等操作明确提示，而非导出后静默丢失邮件和成员关系。

### 11.6 邮件审核模式（mailMode=review）

- AC-34：审核模式下轮次正常结束不投递、不触发任何收件成员；本轮邮件进入待审核（reviewing），群暂停且原因为 mail_review，任务停在 ready_to_commit。
- AC-35：同批无拒绝 → 定稿后立即投递（与该发件人此前 deferred 的邮件一并投递），后续流程与自动模式一致。
- AC-36：同批存在拒绝 → 同意的邮件转 deferred（本轮不投递）；拒绝原因与同意清单以 `[system messages] 用户拒绝「x」原因：…；用户同意「y」-> 已加入本轮待发箱…` 注入发信人子会话并触发其再生成一次；deferred 邮件在发信人下一轮审批通过时一并投递，不重复发送。
- AC-37：拒绝原因必填；被拒邮件在群页折叠展示（不删除、不撤回）；审核期间不自动投递，进程重启后重新进入待审核而非补投。

## 12. 首版不做与实施前最后确认项

首版不做：动态成员管理、成员别名更改、独立 Agent 配置副本、群组整体复制/导入导出、真正外部邮箱、多后端进程分布式调度、全文邮件搜索、撤回已投递邮件、把全部子会话推理过程混排到群页。

实施前建议确认本轮新增默认值：

1. 别名创建后固定，长度/规范化/区分大小写规则是否接受。
2. 自动轮次默认 50，以及显式重置的计数方式是否接受。
3. 允许自发邮件、首版群输入仅文本、Agent 被群引用时禁止删除是否接受。
4. 群任务排队响应需扩展现有交互响应类型；旧第三方客户端如直接操作群成员，需要升级以识别 queued。

以上不影响已确认的核心产品规则，但在实施前明确可减少返工。获得对本轮设计和代码实施的许可后，再开始编码；本文写入不等于实施授权。
